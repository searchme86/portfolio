  • BEM 방법론 적용을 통한 CSS 컨벤션 정의

    페이지 재작업 시간 20분(30분→10분), 디자인 완료 평균 기간 2.5일(3일→0.5일) 단축

    좋은 품질의 마크업과 스타일 산출물을 목표로 사이트 운영업무 한 적 있습니다. 마크업 1건을 수정하려고 해당 클래스명을 검색하면, 같은 스타일의 다른 클래스가 여러 발견하곤 했습니다.

    불필요하게 중복된 속성이 검색되어 유지보수가 좋지 않았습니다. 기존 정의된 속성을 가져다 쓰는 운영업무 특성상, 작업자가 중복되게 입력할 여지가 있었습니다.

    이를 해결하기 위해 BEM방식을 적용하기로 마음먹었습니다. 마크업 구조를 염두에 두며 스타일 정의하는 BEM으로 클래스 컨벤션을 정의하고 사용해, 페이지 재작업 시간을 20분(기존 30분에서)으로, 디자인 완료 평균 기간을 2.5일(기존 3일에서)로 단축했습니다.

  • 프로젝트 의존성 라이브러리 Settings 파일 수정

    스크립트 기능 오류 1건 해결

    테이블 헤더 영역에 마우스 호버하면, 말풍선을 보여주는 툴팁(tooltip) 플러그인 적용 업무가 있었습니다. 텍스트 너비가 유동적으로 달라지기 때문에, 이에 맞게 툴팁 위치도 변경해야 했습니다.

    그러나 라이브러리에서 해당 기능을 실행하는 헬퍼함수가 없었습니다. 툴팁 위치를 이동하는데, 힌트를 얻고자 Settings(환경설정) 파일을 훑어봤습니다.

    대상이 생성될 때, 위치(position) 결정하는 속성이 있지 않을까 궁금했기 때문입니다. 인스턴스 만드는 생성자 함수값을 변경하면서 테스트 해봤는데, 브라우저에서 다른 위치로 이동해 출력됨을 확인했습니다.

개발 프로젝트 진행 시, 주요 담당 역할
  • 프로젝트 코드 활용해, 스크립트 개발자 업무 8건 지원

    삼성카드 운영 프로젝트에서 마크업과 해당 UI 스크립트 업무를 수행한 적이 있습니다. 작성한 스크립트가 프로젝트 제품으로 적합한지 점검받고 싶었고, 이미 다른 곳에서 구현된 사례가 있는지 확인하기 어려웠습니다.

    코드 신뢰성을 확보하고 중복을 방지하기 위해, 프로젝트 가이드 문서를 검색했습니다. 스스로 참고 자료를 얻기 위해, 사이트의 모든 페이지를 확인했습니다.

    직접 코드를 작성하면서, 보완할 점이 없는지 획득한 자료와 비교해보곤 했습니다. 혼자서 끝까지 완성한 이후, 매번 개발자에게 코드 리뷰를 받았습니다. 그 결과 스크립트 8건 업무를 성공적으로 수행할 수 있었습니다.

실패 경험
  • 프로젝트의 A-Z를 경험한 6주

    6주간, 개발 포트폴리오를 만드는 프로젝트에 참가해, 프로젝트의 A-Z를 경험하고 크게 배운 경험이 있습니다.

    작업 가능 기간, 서로 개발숙련도를 따져보기에 앞서, 어떤 상품을 만들어야 할지, 공통된 의견 도출이 힘들었습니다. 다분히 어려웠던 점을 팀원에게 요청할 수밖에 없었는데, 결국 중도하차 인원이 발생했고, 다른 참가 팀 대비 진척도는 늦었습니다.

    • 첫째, 팀원은 제품에 대해 공통된 의견과 개념을 갖고 있어야 합니다. 즉 제품이 갖는 목적을 팀원이 공유해야, 관련된 디자인과 상품 기능을 정의할 수 있기 때문입니다.
    • 둘째, 프로젝트 이슈관리를 포함해 환경설정을 문서로 정리합니다. 백엔드 개발자의 프론트개발 환경셋업을 요청했는데, 당시 정리된 내용이 없어, 원격으로 해결하느라 애를 먹은 적 있습니다.
    • 셋째, 프로젝트에 사용되는 개발언어 선택기준이 개인 성숙도가 높고 성과를 빨리 만드는 언어를 사용합니다. 당시 타입스크립트를 학습 중이었는데, 프로젝트에서 테스트하고 싶은 욕심이 있었습니다.
    • 넷째, 어느 CEO의 말처럼, 글은 기록으로 남기 때문에 전달에 오해가 생기지 않도록 심사숙고해 작성합니다. 대화가 요구되는 영역에서는 말로 표현하는 것 효과적일 수 있겠다고 생각했습니다.
성격의 장단점
  • 알고 있는 지식의 원리를 설명하고 이해시키려고 애씁니다

    지식공유 활동이나 스터디처럼 개념의 원리를 알려주고 문제를 해결하는 과정에 관심이 많습니다. 원리를 이해하고 습득하는 과정은 낯설고, 어렵지만, 이를 통해 자기 것으로 만들었다는 자기 자신감이 이런 성격을 갖게 된 동력입니다.

  • 상대방에게 도움 주려는 좋은 의도와 잘하려는 욕심이 앞서게 되면, 주어진 일의 범위를 넘어서거나 불필요한 내용을 말붙이곤 합니다

    이러한 점은 해당 담당자의 업무 권한을 침해할 여지가 있고, 업무 의도에 맞지 않아 다시 일해야 할 수 있습니다. 이것을 해결하기 위해,

    • 첫째, 사람을 배제하고 일 자체가 달성할 업무 목적에 집중합니다.
    • 둘째, 첫째 목표가 달성된 이후, 개선 및 추가적인 여지가 있으면, 담당자에게 해당 사항을 알려줍니다
    • 마지막으로, 계속 업무가 필요하거나 그렇지 않을 때 따라 작업을 진행합니다.

    위 순서를 유념하여 일합니다.

개발에 관심 두게 된 계기와 노력
  • 개발에 관심 두게 된 계기
    "이거 내가 수정 할 수 있을까?"

    주말 평균 100명가량의 수강생이 찾는 학원에서, 회계 솔루션 제품을 사용하며, 수납 업무 일한 적 있습니다. 일할 때 어려웠던 점은, 사람마다 사정이 다양하게 있어 프로그램에 정의된 기능으로 처리 불가한 사례가 종종 발생했습니다.

    이런 경우 해당 내용을 메모해 두는 것으로 문제 해결했습니다. 사용 중인 솔루션 콤보박스(Select)에 option 하나 더 추가 할 수 있었다면, 굳이 수작업이 필요 없었습니다.

  • 개발자로 성장하기 위해 어떤 노력
    웹 퍼블리싱, 논리적 구조로 HTML 작성

    취업 성공 패키지를 수료 후, 첫 개발회사에서 마크업 업무를 맡았습니다. 홈페이지의 일부 마크업 수정을 시작으로, 홈페이지 리뉴얼, 이메일 뉴스레터 로 영역을 키워갔습니다.

    HTML과 JQuery를 통해, 프론트 개발 업무 수행

    한국신용정보원 프로젝트를 통해, 주도적으로 프론트 개발업무를 수행한 적 있습니다. 뷰(View) 관련 업무를 진행하면서, 마크업을 설계하고 스크립트와 플러그인을 사용해, 동적 웹 페이지 개발업무를 성공적으로 마무리했습니다.

    프로젝트 별, 업무 관점 차이를 경험

    삼성카드 사이트 운영을 맡으면서 프로젝트의 형태가 구축/운영 간, 업무 관점 차이가 존재함을 경험했습니다. 타 직무 이해자(기획자/디자이너/프론트개발자)와 협업하면서 효과적으로 의사소통하고 팀원으로 일하는 방법을 배웠고 고민했습니다.

관심 있는 개발 분야
  • 관심 있는 분야는 프론트 뷰(View) 개발자입니다

    다양한 프로젝트(구축 2건, 개선/유지보수 4건, 운영 1건)를 경험하며, HTML로 의미 구조를 설계하고, 자바스크립트가 사용하기 쉬운 마크업을 작성했습니다. 디자인 가이드 맞게 컴포넌트 마크업 작업을 진행했습니다.

  • Vue프로젝트를 통해, 컴포넌트 마크업의 중요성을 배움

    1년가량의 삼성생명 VueJs 프로젝트에서, 공통 컴포넌트 설계를 위해 프론트 개발자와 협업한 적이 있습니다. 퍼블리셔가 작성한 마크업을, 프론트 개발자가 Vue컴포넌트로 변경하고, 완성된 부품을 페이지로 조립하는 업무였습니다.

  • 3개월 JQuery 토이 프로젝트를 통해, 컴포넌트 단위 개발 장점을 이해

    실무에서 정적(Static) 페이지를 구축하면서, HTML을 동적으로 다루는 스크립트 역량에 관심 두게 되었습니다. 3개월 동안 JQuery 토이 프로젝트를 만들며, DOM 제어하는 스크립트 작성과 프로젝트 구조설계를 경험했습니다.

  • 3개월 React 토이 프로젝트를 통해, 유지보수 관점의 코드설계 중요성을 이해

    데이터 CRUD를 연습하고, 리액트 학습 목적으로, 중고마켓을 주제로 웹 서비스를 구축했습니다. 개발스택은 입문자들이 웹 서비스를 구현하기 쉬운 MERN(MongoDB, ExpressJs, ReactJs, NodeJs)으로 선택했고, DB 설계와 배포까지 웹 개발 프로세스를 경험했습니다.

내가 생각하는 좋은 코드란
  • 핵심 로직과 의도가 명확하게 읽히는 코드

    개발자는 코드로 의사소통하기 때문에, 핵심이 드러나도록 작성합니다. 프로젝트 실무를 겪으며, 다른 사람의 코드를 이해하는 것도 업무 일부라는 점을 경험했습니다. 핵심이 뚜렷하면 개선 사항을 발견하기 쉽고, 팀원 간 피드백 주고받기 편합니다.

  • 코드 흐름을 이해하기 좋은 구조로 작성

    기능을 정의하는 곳, 사용하는 곳을 구분해 입력할 경우, 실행오류를 파악하기 쉽고 유지보수가 편하기 때문입니다.

  • 값을 주고, 받을 때, 사라지는 값이 없고, 타입 안정성을 보장하는 코드

    함수 인자에서 스프레드 연산자로 값을 받는 경우, 스프레드 연산자에서 인자값을 규정하는 조건이 없어, 값이 사라질 수 있거나 다른 타입의 값을 받을 수 있다고 코드리뷰 받았습니다. null/undefined 처리 조건과 같은 방어코드를 작성하거나, 타입스크립트 사용해 문제 해결할 수 있습니다.

  • 외부 코드 사용할 때, 코드 신뢰성과 안정성을 체크

    주소 검색 모달을 구현할 때, 다음 주소 검색 라이브러리를 소개한 블로그 코드를, 프로젝트에 그래도 적용 한 적 있습니다. 코드 리뷰어 관점에서는 해당 구문을 더 쪼개어 표현할 수 있었는지, 코드 안정성은 보장할 수 있는지, 신뢰할 수 있는 코드인지 점검이 필요하다는 피드백 해주었습니다.

    • 연산자를 연달아 중복해 쓰지 않는 코드
    • 로직 의미를 유추할 수 있는 의미의 함수/변수 이름
    • 테스트할 수 있는 코드
    • 보안성을 고려한 코드
